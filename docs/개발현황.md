## 기존 데이터 변경 내역

승인받은 삭제 정책 두 개를 적용해 검사했습니다. 업로더와 회사 소유자의 삭제 허용, 같은 회사 일반 사용자의 직접 삭제 차단, 다른 회사의 삭제 차단은 확인했습니다. 그러나 기존 `files_update` 정책은 같은 회사 일반 사용자가 `uploaded_by`를 자신으로 바꾸는 것을 허용합니다. 업로더 기반 삭제 제한을 우회할 수 있어 이번에 추가한 정책 두 개를 다시 제거했습니다.

철회 직후 추가한 정책 수가 0이며 임시 사용자·회사·프로젝트가 남지 않았음을 확인했습니다. 기존 정책과 사용자 자료는 변경하지 않았습니다. 삭제 정책의 적용 이력은 Supabase 마이그레이션에 기록됐습니다. 철회 도구가 두 번 만료 오류를 반환해 기본 SQL 도구로 해당 정책만 제거하고 실제 상태를 재확인했습니다. Supabase 보안 점검 도구는 경고 0건이었으나 위 권한 조합 문제는 별도 시나리오 검사에서 발견했습니다.

[삭제 권한 보완안](삭제권한보완안.sql)을 추가 승인받아 적용했습니다. 업로더·프로젝트·저장 경로·파일 ID 변경을 막는 트리거와 삭제 정책 두 개가 추가됐습니다. 기존 정책은 유지했으며 업로드 상태 변경은 계속 허용합니다. Supabase 마이그레이션 이름은 `phase_a_guard_source_identity_and_delete_permissions`입니다.

실제 원본 삭제는 사용자가 입력할 수 있는 파일 메타데이터 대신 Storage가 기록한 `owner_id`를 확인합니다. 프로젝트 폴더 일치도 검사합니다. 다른 파일 경로를 가진 메타데이터를 새로 등록해 삭제 제한을 우회하지 못하도록 같은 삭제 정책을 보강했습니다. 마이그레이션 이름은 `phase_a_require_storage_owner_for_source_delete`입니다.

보완 후 실제 데이터베이스에서 삭제 허용·차단 4개, 식별 정보 변경 차단 4개, 업로드 상태 갱신 허용 1개로 총 9개 검사를 통과했습니다. 임시 자료는 전부 롤백했습니다. 실계정으로 Storage까지 연결한 삭제 통합 검증 후에만 `ENABLE_SOURCE_DELETE=true`를 Preview에 설정합니다.

실제 로그인 계정 설정이 미뤄졌으므로 성공한 실계정 업로드로 보고하지 않습니다.
