## 기존 데이터 변경 내역

승인받은 삭제 정책 두 개를 적용해 검사했습니다. 업로더와 회사 소유자의 삭제 허용, 같은 회사 일반 사용자의 직접 삭제 차단, 다른 회사의 삭제 차단은 확인했습니다. 그러나 기존 `files_update` 정책은 같은 회사 일반 사용자가 `uploaded_by`를 자신으로 바꾸는 것을 허용합니다. 업로더 기반 삭제 제한을 우회할 수 있어 이번에 추가한 정책 두 개를 다시 제거했습니다.

철회 직후 추가한 정책 수가 0이며 임시 사용자·회사·프로젝트가 남지 않았음을 확인했습니다. 기존 정책과 사용자 자료는 변경하지 않았습니다. 삭제 정책의 적용 이력은 Supabase 마이그레이션에 기록됐습니다. 철회 도구가 두 번 만료 오류를 반환해 기본 SQL 도구로 해당 정책만 제거하고 실제 상태를 재확인했습니다. Supabase 보안 점검 도구는 경고 0건이었으나 위 권한 조합 문제는 별도 시나리오 검사에서 발견했습니다.

[삭제 권한 보완안](삭제권한보완안.sql)을 추가 승인받아 적용했습니다. 업로더·프로젝트·저장 경로·파일 ID 변경을 막는 트리거와 삭제 정책 두 개가 추가됐습니다. 기존 정책은 유지했으며 업로드 상태 변경은 계속 허용합니다. Supabase 마이그레이션 이름은 `phase_a_guard_source_identity_and_delete_permissions`입니다.

실제 원본 삭제는 사용자가 입력할 수 있는 파일 메타데이터 대신 Storage가 기록한 `owner_id`를 확인합니다. 프로젝트 폴더 일치도 검사합니다. 다른 파일 경로를 가진 메타데이터를 새로 등록해 삭제 제한을 우회하지 못하도록 같은 삭제 정책을 보강했습니다. 마이그레이션 이름은 `phase_a_require_storage_owner_for_source_delete`입니다.

보완 후 실제 데이터베이스에서 삭제 허용·차단 4개, 식별 정보 변경 차단 4개, 업로드 상태 갱신 허용 1개로 총 9개 검사를 통과했습니다. 임시 자료는 전부 롤백했습니다. 실계정으로 Storage까지 연결한 삭제 통합 검증 후에만 `ENABLE_SOURCE_DELETE=true`를 Preview에 설정합니다.

실제 로그인 계정 설정이 미뤄졌으므로 성공한 실계정 업로드로 보고하지 않습니다.

## Phase C 기획서 편집·버전 관리 — 2026년 10월 23일 추가

프로젝트에 `기획서 편집` 탭을 추가했습니다. 직접 기획은 저장된 실제 제품 브리프에서 시작하며 가상 시험·효능 수치를 넣지 않습니다. 작성 필요 문구는 승인 전에 바꿔야 합니다.

- 구좌 제목·본문·비주얼 가이드 편집, 승인 근거 연결과 원문 인용 확인
- 구좌별 승인·승인 해제. 승인한 구좌는 잠기며 다른 구좌의 편집으로 변경되지 않음
- 전체 생성과 구좌 하나만 재생성. 구좌 재생성은 다른 구좌 및 승인 상태를 보존
- 수정·승인·재생성·복구 때마다 새 버전 추가. 오래된 부모 버전의 저장을 충돌로 처리
- 이전 버전 조회·복구, 수정 내용 취소, 저장 충돌 시 미저장 JSON 백업
- 기획서 HTML 및 버전 JSON 다운로드. HTML은 오프라인에서 열어 인쇄·PDF 저장 가능하며 미승인 내용은 검토용으로 표시
- 과거 버전의 제품 브리프·원본 인용·페이지·승인자·승인 시각 보관. 내려받는 HTML의 입력 내용 이스케이프 및 외부 리소스 차단

`/api/plans`는 사용자 세션과 프로젝트·제품 권한을 확인합니다. `ENABLE_PLAN_STORAGE=false`가 기본입니다. 사용자가 [기획서 버전 저장 추가안](기획서버전저장추가안.sql)을 승인하여 `phase_c_planning_versions_and_approval_guards` 마이그레이션으로 실제 Supabase에 적용했습니다. 새 테이블 하나와 접근 정책·이력 보호 트리거를 추가하며 기존 9개 테이블·자료·정책은 변경하지 않습니다. 기존 `sections` 테이블에도 쓰지 않습니다. 타입 파일은 변경 후 실제 Supabase에서 다시 생성했습니다. 실제 권한 검사 통과 후 로컬 환경의 버전 저장을 활성화했습니다. Preview 환경 반영은 배포 재개 승인 후 진행합니다.

검증 범위를 구분합니다. 현재 단위/API 모의 및 로컬 PostgreSQL 검사 총 73개가 통과했습니다. 이 중 신규 버전 저장 SQL 검사는 PGlite 로컬 DB의 역할·사용자·기초 테이블 모형으로 16개를 확인했습니다. 실계정 테스트를 대신하지 않습니다. 이후 실제 Supabase에서 동일 회사 회원 조회, 다른 회사 접근 차단, 승인·개별 재생성·복구, 원문·승인자 위조 및 수치 차단 등 19개 검사를 추가로 통과했습니다. 임시 사용자·회사·제품·원본·근거·버전은 모두 롤백했고 잔여 0건을 확인했습니다. 보안 점검 경고도 0건입니다. 실제 REST API에서도 기존 자료 9종의 비로그인 노출 차단, 새 기획서 버전 조회 차단, 원본 업로드 차단으로 11개 검사를 통과했습니다. 최신 빌드의 데스크톱·모바일 브라우저 검사 14개가 통과했습니다. 이 중 기획서 편집 검사 4개는 실제 React 컴포넌트를 테스트 전용 진입점으로 묶고 API를 모의 응답합니다. 서비스에 공개하는 체험 라우트를 추가하지 않았습니다.
